## 🛡️ Reporting a Vulnerability

We take security vulnerabilities seriously. If you discover a security issue, please report it **privately** to ensure responsible disclosure.

### How to Report

**DO NOT** create a public GitHub issue for security vulnerabilities.

Instead, please follow one of these methods:

#### Method 1: Private Vulnerability Reporting (Recommended)

1. Go to the [Security tab](https://github.com/natalinio/aisemanticlayer/security) on GitHub
2. Click **"Report a vulnerability"**
3. Fill out the form with details:
   - **Type of vulnerability** (e.g., code injection, information disclosure)
   - **Affected component** (e.g., Python scripts, TMDL generation)
   - **Steps to reproduce**
   - **Potential impact**
   - **Suggested fix** (if you have one)

#### Method 2: Email

Send an email to:
- **Email**: andrea.natali@avanade.com
- **Subject**: `[SECURITY] Power BI AI Developer - <Brief Description>`

Include:
- Detailed description of the vulnerability
- Steps to reproduce
- Affected versions
- Potential impact
- Your contact information (optional, but helpful for follow-up)

### What to Expect

1. **Acknowledgment**: We'll acknowledge receipt within **48 hours**
2. **Investigation**: We'll investigate and assess the severity
3. **Updates**: We'll provide regular updates on progress (at least every 7 days)
4. **Resolution**: We'll work on a fix and coordinate disclosure timing
5. **Credit**: If you wish, we'll credit you in the security advisory and CHANGELOG

### Response Timeline

| Phase | Target Timeline |
|-------|----------------|
| Initial acknowledgment | 48 hours |
| Severity assessment | 7 days |
| Fix development | 14-30 days (depending on severity) |
| Public disclosure | After fix is released |

## 🚨 Security Considerations

### Data Privacy

This project processes:
- **Functional specifications** (may contain business-sensitive information)
- **CSV mock data** (generated with faker library, no real data)
- **TMDL files** (semantic model metadata)

**Recommendations**:
- ⚠️ **Do NOT commit** real customer data, credentials, or API keys
- ✅ **Use mock data** generated by the project's scripts
- ✅ **Review `.gitignore`** to ensure sensitive files are excluded

### Code Execution

This project includes:
- **Python scripts** (run locally in your environment)
- **GitHub Copilot agent** (accesses files in your workspace)

**Security practices**:
- ✅ **Review generated code** before execution
- ✅ **Use virtual environments** (`.venv/`) to isolate dependencies
- ✅ **Keep dependencies updated** (run `pip install --upgrade -r requirements.txt`)
- ⚠️ **Do NOT run scripts** from untrusted sources

### TMDL/DAX Injection

While unlikely, be aware:
- **TMDL generation** uses templates and string formatting
- **DAX generation** constructs measure expressions from specifications

**Mitigation**:
- ✅ Agent validates syntax against references
- ✅ User approval required before applying changes
- ✅ Manual review step (Step 6) validates all generated code

## 🔐 Best Practices for Users

### 1. Keep Dependencies Updated

```powershell
# Check for outdated packages
pip list --outdated

# Update all dependencies
pip install --upgrade -r requirements.txt
```

### 2. Review Generated Code

Always review:
- **TMDL files** before opening in Power BI Desktop
- **Python scripts** before execution
- **DAX measures** before deploying to production

### 3. Use Git Branching

Never work directly on `main`:
```bash
git checkout -b feature/your-feature
# Make changes, test thoroughly
# Create PR for review
```

### 4. Protect Credentials

If you extend the project with data source connections:
- Use **environment variables** for credentials
- Use **Azure Key Vault** or similar secret management
- Never hardcode passwords or connection strings

### 5. Scan for Vulnerabilities

For Python dependencies:
```powershell
# Install safety tool
pip install safety

# Scan for known vulnerabilities
safety check
```

## 📊 Vulnerability Disclosure Policy

### Public Disclosure

After a security fix is released:
1. We'll publish a **Security Advisory** on GitHub
2. We'll update the **CHANGELOG.md** with fix details
3. We'll create a **new release** with the patch
4. We'll notify users via GitHub Releases

### Severity Levels

We follow the [Common Vulnerability Scoring System (CVSS)](https://www.first.org/cvss/):

| Severity | CVSS Score | Response Time |
|----------|------------|---------------|
| **Critical** | 9.0 - 10.0 | 24-48 hours |
| **High** | 7.0 - 8.9 | 7 days |
| **Medium** | 4.0 - 6.9 | 30 days |
| **Low** | 0.1 - 3.9 | 90 days |
